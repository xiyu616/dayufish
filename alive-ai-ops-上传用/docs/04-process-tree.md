# 坑 4：一个子进程崩了，能把宿主一起带走

这是我代价最大的一次事故。整台机器上的 AI 失联了一个小时，我以为是网络问题。

## 现场

时间线（从系统事件日志拼出来的）：

```
23:25:41  python.exe 崩溃，异常码 0xc0000005（访问冲突），故障模块 c10.dll
23:25:42  宿主进程退出，退出码 4294930435
23:25:42  界面报「应用无法启动或已意外停止」
```

`c10.dll` 是 PyTorch 的核心库。那会儿正在做一个"放大出图"的操作，
显存打满，torch 直接崩在底层。

如果只是 torch 崩了，我重启一下就行。问题是：**它把宿主也带走了。**

## 根因：进程树

我用"工具调用"的方式起了一个重型子进程（图像生成服务）：

```
宿主(DashScope/DSH) -> shell -> WScript -> 批处理 -> ComfyUI(python/torch)
```

整条链是**父子关系**。子进程崩在底层异常上，父进程跟着完蛋 —— 这叫**进程树连坐**。

关键点：宿主不是自己死的，是**被它自己派出去干活的孙子辈拖死的**。

## 为什么难发现

- 宿主日志里只有一行 "host exited"，没有原因
- 崩的是孙子进程，宿主的日志根本不知道
- 看起来像"程序自己抽风"，其实有明确的因果

你要去翻 **Windows 事件查看器 → 应用程序日志**，才能看到那个 python.exe 的崩溃记录。
两个时间点差 1 秒，这就是铁证。

## 解法

### 1) 重型子进程必须 detached

不要让一个可能吃掉 8G 显存/内存的进程，成为你主进程的后代。

- Windows：`Start-Process` 起一个新的独立进程树；或用 `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP`
- 用 `pythonw.exe` 起后台脚本，别用 `python.exe` 挂在 shell 下
- 批处理里再起一层也要注意，`cmd /c` 起的还是子进程

### 2) 别在同一进程里干"占满资源"的活

出图、转码、训练、大文件索引 —— 这些要么独立进程，要么独立机器。

### 3) 峰值要一步步加，别一次顶到上限

我的出图流程后来改成：

```
512×512 草稿（确认构图、确认不崩）
  -> 768×1152 中档
  -> 才考虑更大
```

直接上 1024×1536 的那次，就是 0xc0000005。

### 4) 干完就关，别留着

每轮结束 `Stop-Process` 掉那个服务进程。留着就是留一个随时会崩的雷。

## 同类退出码

后面又崩过几次，退出码各不相同，但都是同一族：

| 退出码 | 十六进制 | 场景 |
| --- | --- | --- |
| 1073807364 | 0x40010004 | 调试器/异常终止 |
| 3758096392 | 0xE0000008 | 硬件/驱动级异常 |
| 4294930435 | 0xFFFF0003 | 被带走时的宿主退出 |

看到这族码，**先去翻事件日志找那个真正崩掉的子进程**，别在宿主自己的日志里瞎找。

## 一句话教训

**你的主进程不该为任何一个"可选的、重的、会崩的"子任务的失败买单。**
把它们踢出进程树。
